# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

ImmersiveMap is a Swift + Metal vector-tile map engine for SwiftUI: globe/flat presentation, labels, starfield, extruded buildings with directional shadows, SwiftUI markers, avatar markers, routes, 3D scene models, and video/still export. It is the **public** Swift Package `artembobkin/ImmersiveMap` (library product `ImmersiveMap`), Swift 6 tools with language mode v6 (strict concurrency), platforms iOS 18 (UIKit) and native macOS 15 (AppKit)

Because the repo is public: never commit tile-provider API keys, bearer tokens, credentials, `LocalSecrets.plist`-style files, or build artifacts (`.build/`, `DerivedData/`, `Traces/`).

## Commands

`swift test` runs the whole suite natively on macOS, the Metal-backed tests included, since every build of the package compiles the shaders (`MetalLibraryPlugin`, below). To run it on iOS, or as CI's Xcode jobs do, use xcodebuild against the SwiftPM-generated workspace:

```sh
xcodebuild test -workspace .swiftpm/xcode/package.xcworkspace -scheme ImmersiveMap-Package \
  -destination 'platform=macOS'                          # full suite, native macOS
xcodebuild test -workspace .swiftpm/xcode/package.xcworkspace -scheme ImmersiveMap-Package \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro'   # full suite, iOS (runs UIKit-gated tests)
```

CI (`.github/workflows/ci.yml`) runs on the `macos-26` image, whose default Xcode is the one the code is developed with (Xcode 26.6, Swift 6.3). Keep the two the same: strict concurrency diagnostics differ between Swift versions, and a mismatch shows up as a CI build that fails on code the local build accepts. When the local Xcode moves, move the image (or select the Xcode with `DEVELOPER_DIR`) in the same change. Two more jobs build the portable package (see Portable targets) on Linux, `linux-test` and `wasm-test`, in the `swift:6.4.2-noble` container, the release that package was brought up with: they are what fails when a change brings an Apple-only API into it, since the macOS jobs never build it.

`.githooks/pre-push` runs `swift test` before every push and refuses the push when it fails. It is installed once per clone with `git config core.hooksPath .githooks`, and `git push --no-verify` skips it when that is wanted.

The picture tests (an offscreen frame judged by its pixels) are skipped by default and are never run in CI. To run them once by hand, set `IMMERSIVE_MAP_RUN_PICTURE_TESTS=1` (with the `TEST_RUNNER_` prefix for xcodebuild). Never write new ones, see `.claude/rules/tests.md`.

To run the map in an app, open `ImmersiveMap.xcworkspace` and run `Develop/ImmersiveMapDevMac`, the scratch app of the work in progress, or `Develop/ImmersiveMapDevIOS`, its iOS counterpart for a simulator or a device. There are no example apps in the repository, on purpose: the doc comments on the public API are the reference, and `Develop/` is the only app.

## Architecture

A folder's boundary rules, what it owns and what it must not contain, are in the comment on its main type (`RenderFrameEngine` for `Render`, `ImmersiveMapView` for `UI`). Read it before adding a file to a folder.

### Targets

The package follows the standard SwiftPM layout (`Sources/<Target>`, `Tests/<Target>Tests`), so `Package.swift` states no paths. There are two products: `ImmersiveMap`, the engine, and `ImmersiveMapDebug`, the debug panel, linked by the `Develop/` apps and the tests and never by a shipping app, which carries nothing of it. Besides them there are these targets at `package` access, visible to every target of the package and to no app that links a product:

- `ImmersiveMapDebug` (`Sources/ImmersiveMapDebug`): the debug panel over the map, `ImmersiveMapDebugPanel.hud`, installed with `ImmersiveMapView.debugPanel(.hud)`. The engine keeps no panel of its own: it holds what a panel reads and drags (`DebugOverlayControlState`, `DebugOverlayHUDSnapshotStore`, under `Render/Debug`) and the slot a panel fills (`ImmersiveMapDebugPanel`, `ImmersiveMapDebugPanelHost`, `ImmersiveMapDebugPanelRuntime` in `UI/Controllers/ImmersiveMapDebugPanel.swift`, at `package` access), and `Panel/` here fills it: the HUD views of each platform, the zoom badge, the planners that turn a dragged control into settings, the settings export, and the runtime that wires them (`ImmersiveMapDebugOverlayRuntime`). Everything of the engine the panel reads is marked `package`, never `public`, so a type the panel needs is opened to the package and not to the apps. The engine never reaches into this target, and nothing here draws into the frame: the in-frame overlay (`DebugOverlayRenderer`, the tile grid) is still the engine's, under `Render/Debug`.

- `PortableFoundation` (`Sources/PortableFoundation`): what a portable target imports in place of Foundation. It re-exports Foundation on Apple's platforms and FoundationEssentials with the platform's C library elsewhere, since the full Foundation makes a WebAssembly binary of 60 MB. A file that needs what FoundationEssentials lacks (`URLSession`) imports Foundation itself, beside it, and guards that part with `canImport`: `PMTilesArchiveClient` builds everywhere, and only its session and file fetchers are left out where there is no `URLSession`, where the host makes the client over a fetcher of its own (`init(archiveURL:requestHeaders:tileType:fetchRange:)`, tested by `PMTilesArchiveClientFetcherTests`). It also gives the names the engine takes from Foundation on Apple's platforms and that FoundationEssentials lacks: Dispatch, `CFTimeInterval`, QuartzCore's `CACurrentMediaTime`, `NSLock` and the Core Graphics geometry types (`CGFloat`, `CGPoint`, `CGSize`, `CGRect`). Where there is no Dispatch (WebAssembly) it has a `DispatchQueue` with `sync` alone, which is the queue as a lock around a state and nothing more, over the standard library's `Mutex`. The slim build's `NSLock` does nothing only where the runtime has one thread, asked with `_runtime(_multithreaded)`, never by the platform's name: a WebAssembly build with threads must get real locks. A file that takes only the clock from QuartzCore imports QuartzCore under `#if canImport(QuartzCore)`. The geometry types and `NSLock` come from the platform's Foundation, those types alone, except in a slim build (`IMMERSIVE_MAP_SLIM=1`, the one that ships to a browser, since naming Foundation at all adds 46 MB to a WebAssembly binary), where they are the package's own in `CoreGraphicsTypes.swift` and `Lock.swift`. `PortableFoundationTests` holds all three to the same answers, and is written with Swift Testing because XCTest brings Foundation into a test file. It also holds, for every platform, a replacement for each Foundation call the engine used that FoundationEssentials lacks (JSON, trimming, `String(format:)`, file handles and listings, date formatting), written once and run the same everywhere, Apple's platforms included: an engine file uses it, never the Foundation call. `PortableFoundationParityTests` holds them to Foundation's own answers where there is a Foundation to ask. A replacement for a string, the standard library's `replacing(_:with:)`, needs nothing. What only Apple's Foundation does (`Locale.Language`, ICU transliteration) stays on Apple's platforms under `#if canImport(Darwin)`, with a fallback elsewhere that says in its comment what it gives up. An engine file that imports no Metal or UI framework imports `PortableFoundation`, never Foundation or CoreGraphics.
- `simd` (`Sources/simd`): a stand-in for Apple's `simd` module, declared by `Package.swift` only off Apple's platforms, under the same name, so the sources that write `import simd` compile unchanged. It holds only what the engine uses, with Apple's names, meanings and memory layouts. `SimdTests` holds both to the same known answers: it runs against Apple's module on Apple's platforms and against the stand-in elsewhere.
- `os` (`Sources/os`): the same for Apple's `os` module, declared only off Apple's platforms: `Logger`, which writes the notice level and above to the standard error stream, `OSSignposter`, which does nothing, and `OSAllocatedUnfairLock` over the standard library's `Mutex`. `OSTests` runs against Apple's module on Apple's platforms and against the stand-in elsewhere. A file writes `import os`, not `import OSLog`.
- `ImmersiveMapGPU` (`Sources/ImmersiveMapGPU`): the GPU the engine draws with, as protocols (`GPUDevice`, `GPURenderEncoder`, the buffers, textures and pipelines) and plain values a backend conforms to: Metal on Apple's platforms, WebGPU elsewhere. It is shaped after what the engine does with Metal, the state Metal sets while encoding included (cull mode, winding, depth bias, the depth and stencil state), so a feature moves onto it call for call. WebGPU holds that state in its pipelines: its backend makes a pipeline for each combination a draw needs, found by `GPURenderStateTracker`. Making one compiles shaders, tens of milliseconds, so the WebGPU backend prepares the combinations the engine uses before the first frame (the variants a session met, kept between launches), rather than let a new view stall on them. A feature moves onto the interface whole, its pipeline and its drawing, and its `RenderSubsystem` hands it the render core's Metal encoder as `MetalRenderEncoder(encoder)` until the core moves too (the starfield, the horizon, the layers, the polar caps and the ground shadow mask so far). A value that features still on Metal read (`ShadowCascadeAtlas.depthFormat`) is the interface's, and its `+Metal` file gives them Metal's name for it. A type that hands Metal objects to features still on Metal (`ShadowReceiverBinding`) stays in a file of its own and moves with them. A helper that features share (`GroundFogUniform.bind`, `GlobeLightUniform.bind`) takes the GPU encoder, and a `+Metal` file beside it keeps an overload for the features still on the Metal encoder, which goes when the last of them moves. Constant data is passed with `setVertexValue`/`setFragmentValue`, which send the value's stride with zeros after it, never `&value` with the stride as its length, which reads past the value. An array goes into a buffer with `makeBuffer(_:storage:)`, which makes none for no elements. Both stop on a value that holds references (an array, a class, an existential), whose bytes are a pointer and not the data. Every feature makes its resources with the one device the engine builds with its shader library, `SharedRenderResources.gpuDevice`. A value the engine starts to use is added here with what each backend does with it, and what WebGPU lacks (three-component 8-bit vertex formats, triangle edges, depth clamping, ASTC) is said on the type.
- `ImmersiveMapGPUTestSupport` (`Sources/ImmersiveMapGPUTestSupport`): a GPU that draws nothing and logs the calls (`RecordingGPUDevice`, `RecordingRenderEncoder`), with the constant data each call passes. A feature that draws through the interface is tested with it: its pipeline, its buffers, the values its shaders read and its draws, on any platform, with no GPU and no picture (`StarfieldDrawTests`, `HorizonDrawTests`, `LayerDrawTests`, `GlobeCapDrawTests`, `GroundShadowMaskDrawTests`). A feature's draw loop that needs no frame context is a static function taking the encoder, so a test drives it with recorded meshes (`LayerRenderSubsystem.drawLayers`).
- `ImmersiveMapMetal` (`Sources/ImmersiveMapMetal`): the GPU interface over Metal, on Apple's platforms only: a class per interface object holding the Metal object it forwards to (`MetalDevice`, `MetalBuffer`, `MetalRenderEncoder` and the rest), which stays reachable for the code not yet moved and for what only Metal has (the IO queues). The value conversions are in `MetalConversions.swift`, one property per type, held to Metal's values by `ImmersiveMapMetalTests`.
- `PortableImage` (`Sources/PortableImage`): a PNG decoder (`PNGDecoder`, over `PMTilesInflate`) for the platforms without ImageIO, where the terrain tiles are decoded with it: a terrain source off Apple's platforms serves PNG, and the default, Mapterhorn's WebP, waits for a decoder from the host. Apple's platforms keep ImageIO.
- `Mvt` (`Sources/Mvt`): the Mapbox Vector Tile decoder. The zero-copy wire decoder `MvtTileDecoder`, the decoded model, `MvtGeometryDecoder` and `MvtAttributeDecoder` (the per-feature geometry and tag loops live there so they specialize next to the varint reader, never across the module boundary), `MvtValue` and `MvtGeometryType`, and the tile-space geometry `Point`/`Polygon` with the multi aliases, which `Sources/ImmersiveMap/Tile/Parse/TileSpaceGeometry.swift` re-declares as engine typealiases so they shadow QuickDraw's names the way the old in-module declarations did. The target knows nothing of the tile schema's meaning: no layer name, no style.
- `MvtTestSupport` (`Sources/MvtTestSupport`): the test-side encoder, the synthetic fixture tiles and a deterministic generator. A regular target because test targets cannot share sources, and `MvtTests` and `ImmersiveMapTests` both depend on it.
- `PMTiles` (`Sources/PMTiles`): the PMTiles v3 reader, a tool like `Earcut` with no engine dependency. The format as pure functions over `Data` and the HTTP range client `PMTilesArchiveClient` that reads an archive with them, keeping its leaf directories in `PMTilesDirectoryCache`. It hands back decompressed tile bytes, and the engine's `TileDownloader` maps its outcomes onto the tile loader's.
- `PMTilesTestSupport` (`Sources/PMTilesTestSupport`): `PMTilesArchiveWriter`, a writer independent of the reader that builds fixture archives for `PMTilesTests` and `ImmersiveMapTests`.
- `Earcut` (`Sources/Earcut`): the internal earcut port for polygon triangulation, one enum `Earcut` with `tessellate` and `deviation`, no dependencies. `ParsePolygon` reaches it with `import Earcut`, and `EarcutTests` imports the module without `@testable`.
- `TileFlattening` (`Sources/TileFlattening`): the ground flattener, pure geometry with no dependencies. Stacked painted rings go in (`FlattenInput`), and one layer of triangles that do not overlap comes out (`FlatMesh`), cut to a grid for the relief's heights. `GroundFlattening` reaches it with `import TileFlattening`, and `TileFlatteningTests` tests it on its own.

### Portable targets

Off Apple's platforms the package is the targets that know nothing of Metal or SwiftUI, and their tests: `PortableFoundation`, `Earcut`, `ImmersiveMapGPU`, `Mvt`, `PMTiles`, `PortableImage`, `TileFlattening`, the two test support targets, `simd` and `os`. `Package.swift` decides by the platform it is read on, so a Linux machine gets that package by itself (`swift build`, `swift test`), and a Mac building for another platform asks for it with `IMMERSIVE_MAP_PORTABLE=1`. For WebAssembly: `swift build --swift-sdk <wasm sdk> --build-tests`, then the test binary under `wasmkit run --dir <the checkout> --dir /tmp`, named by its absolute path (by a relative one it traps before the first test, with no message), so the Earcut fixtures can be read and the file tests can write. A slim build (`IMMERSIVE_MAP_SLIM=1`) leaves out the XCTest targets and keeps the Swift Testing ones (`PortableFoundationTests`, `PortableImageTests`, `ImmersiveMapGPUTests`). A portable target imports `PortableFoundation`, never Foundation, and guards what a platform lacks with `canImport` (`Dispatch` in `Flattener`, `zlib` in `PMTilesGzip`). `Int` is 32 bits on WebAssembly: a value that can pass 2^31 is typed `Int64` or `UInt64`. A type that holds nothing of the GPU or of a platform's UI (a vertex layout, an atlas description, a run of label ranges) lives in a file that imports neither, beside the GPU code that uses it (`Text/TextLayoutTypes.swift` beside `TextRenderer`), so the code that builds it compiles where there is no Metal: the CPU side of the engine moves off Apple's platforms file by file, and a plain type declared in a Metal file holds every file that names it back.

### Decisions

The code shows how things are wired. These are the decisions behind it, which the code cannot show.

- Dependencies point inward: `UI` → `Render` and the feature folders → `Utils`. A feature folder owns everything of its feature, its model, its math and its drawing (pipelines, shaders, drawers, its `RenderSubsystem`), so there is one place to read for a feature. `Render` knows a feature only through `RenderSubsystem` and `RenderGraphFactory`, a feature never reaches into another feature's GPU internals, feature folders never depend on `UI`, and `Render` holds no networking or platform UI.
- Schema-specific tile logic is confined to `VectorTileAdaptation/`, `Schema/Default` and `Style/Default`. `Render`, `Labels` and `Tile` consume only schema-neutral, already normalized data.
- Rendering is on-demand. The display link is normally paused and resumes for activities (interaction, fades, animations) and one-shot frame requests, so any state change that should redraw must request a frame or register an activity, or the screen does not update.
- Globe and flat are one continuous transition, not a switch. Both render states are always produced and the shaders morph between sphere and plane by a value in [0, 1], so a new layer follows the morph rather than branching on the mode.
- No Swift actors. The frame engine and the `UI` runtimes are main-thread, and tile loading runs in `Task`s off the main thread with its mutable state serialized by plain `DispatchQueue`s. An isolation error is solved within that scheme, not by introducing an actor.
- The decisions of single features live in path-scoped rules, loaded when working on their files: `.claude/rules/tile-placement.md`, `relief.md`, `scene-models.md`, `overview.md`.
- The public API and the map style: `.claude/rules/public-api.md`, loaded when working under `UI/`, `Configuration/`, `Style/` or `Schema/`.

## Conventions and Rules

- Every hand-written `.swift`, `.metal`, `.h` file starts with:
  ```text
  // Copyright (c) 2025-2026 ImmersiveMap contributors.
  // SPDX-License-Identifier: MIT
  ```
- The engine reads its resources through `ImmersiveMapResourceBundle`, never `Bundle.module` directly: `location()` in code that builds off Apple's platforms (the bundle on Apple's, the resources folder `ImmersiveMap_ImmersiveMap.resources` or the one `IMMERSIVE_MAP_RESOURCES` names elsewhere, looked up by `ResourceDirectory`), `bundle()` in the Metal code, which needs the bundle itself for the shader library. The resources travel with the engine in its one bundle, and in an app that bundle is in the app's `Contents/Resources`: an app looks there and nowhere else, and only a program that is no app (the tests, a command-line tool) takes `Bundle.module`. SwiftPM's command-line accessor looks beside an app's `Contents`, where code signing allows nothing, and then at the build folder compiled into the binary, so an app must never reach it. An app without the bundle gets an error: the map view shows it in place of the map (`RendererUnavailableView`), an export throws it, nothing stops the process. A new resource file or directory is registered under `resources:` in `Package.swift`, otherwise it silently doesn't ship.
- The shaders are not resources. The build tool plugin `MetalLibraryPlugin` (`Plugins/`) compiles every `.metal` file of the target with `xcrun metal` into the one `default.metallib` of the resource bundle, under Xcode and `swift build` alike, for the platform the build settings name (macOS under SwiftPM's command line). A new shader folder goes into the target's `exclude:` list in `Package.swift`, and a shader finds its headers by relative `#include` paths. When the bundle holds no library, `RendererSetup.makeLibrary` takes the app's main library only if it holds the engine's shaders, and otherwise throws. An app that adds the package in Xcode is asked once to trust the plugin.
- Never change the code on your own. A request to look into something, to find a cause, to think about an approach or to propose a fix is answered with an investigation and a proposal, and nothing in the working tree changes until the person at the screen says to go ahead with it, in their own explicit word. A request that asks for a change outright is that word. The same holds for a follow-up fix noticed along the way: name it and wait.
- Never commit, run tests or push on your own. A change is left in the working tree, built if a build is needed to check it, and reported. The person at the screen looks first and says when to commit, which tests to run, and when to push, each one its own explicit word.
- The user documentation is `Documentation/`, short Markdown pages of the maintainer's. Editing it is allowed: when a change makes a statement there wrong, or adds something a map's author needs to know, update the page in the same change, in the pages' own short style, and say which page and which statement in the report. The doc comments in the code are the API reference, and there is no DocC catalog. `Assets/` holds the README's images, AVIF written by `Tools/ReadmeFrames`.
- Never edit `README.md`, `CHANGELOG.md` or any other `.md` file except this one, the rules under `.claude/` and the pages of `Documentation/`. When a change makes a statement in one of them wrong, leave the file as it is and say which file and which statement in the report.
- Never launch an app or take screenshots. Building it to check that it compiles is where it stops. Rendering is judged by the person: say which app to run (`Develop/ImmersiveMapDevMac` for work in progress), what the frame should look like, and ask for a screenshot.
- A technical value a map's author may want to tune (a shadow coverage, a fade's zoom range, a band's width, a distance threshold, an animation's duration) is a setting reachable from SwiftUI, not a constant in the engine. It lives in `ImmersiveMapSettings` (or the style, for how the map draws) with a sensible default and a doc comment that says what it does and when to change it, and an `ImmersiveMapView` modifier sets it in place: an optional parameter of the modifier for its group, so the author writes `.shadows(maxCasterHeightMeters: 120)` without building a settings object, and an omitted value is left as configured rather than reset. When such a value is added or found hard-coded, expose it this way in the same change. Values that only make sense while tuning (a debug override) stay in the debug panel.
- The public API is not frozen. Refactoring it is allowed, breaking changes included: a public symbol may be renamed, removed, reshaped or given a different signature when the design calls for it, and no deprecation shim or parallel old API is required. Anything `internal` can be reshaped freely as before.
- Never use a semicolon to join two clauses in prose (documentation, comments, commit messages, UI strings, replies): write two sentences instead. Semicolons in code are fine.
- Never use an em dash (U+2014, the long dash) in any text: documentation, comments, commit messages, changelog entries, UI strings. Rewrite with a comma, a colon, parentheses, or a second sentence instead.
- English everywhere: doc comments, inline comments, assertion messages, `fatalError` and log text, commit messages, documentation. Any other language belongs in the repository only as data, meaning localized map strings (`"ru"`, `"de"`, `"ja"` and the rest of the name entries, style keywords matched against tile properties) and test fixtures that exist to exercise non-ASCII text.
